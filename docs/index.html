Scope

01 / 06

Five tool groups, one safety model

Organized the way a NAS owner thinks about daily operations. Every mutating operation plans first; read operations run directly.

GroupCovers
systemConnectivity & system. SSH check, OS/hardware report (CPU, memory, thermals, disks), and storage-pool health across mdadm RAID, LVM, btrfs, and block devices.
dockerContainers, images, networks, compose. Full lifecycle: list, inspect, logs, start/stop/restart, remove; image pull/remove; network create/remove/connect/disconnect; compose up/down/restart.
filesShares & data. Browse, measure, search; SFTP upload/download (chroot-aware); rsync-style sync with a built-in cp fallback; ffmpeg thumbnails rendered on the NAS.
backupArchives & schedules. tar.gz creation, listing, verification (checksum + entry count), restore, and managed recurring cron jobs that preserve your existing crontab entries.
networkHost networking. Interface inventory with IPv4/IPv6 scopes, both routing tables, and listening TCP/UDP sockets with owning processes.

Safety

02 / 06

Dry-run first, then confirm

Every mutating tool is a two-phase machine. Nothing destructive happens on the first call — ever.

Injection-proof by construction. Every user value — paths, container names, image tags — passes through POSIX single-quote escaping before it touches a shell. Backup job names are restricted to [A-Za-z0-9._-] and cron expressions validated as exactly five fields, because both end up inside shell scripts and crontab lines.

Root paths are refused outright. files.remove will not plan a deletion of /, a bare share root (/volume1), top-level system directories, or UGOS-managed directories like @docker — it rejects before planning.

Pinned by fingerprint. Optionally pin the SSH host key (hostKeySha256); comparisons are padding-insensitive so the canonical ssh-keygen -lf output works as-is.

Structure

03 / 06

A small, layered codebase

One module per tool group. A narrow executor interface so the test suite runs against a fake — no NAS required. 

src/
├── server.ts              entrypoint: stdio + optional stateless HTTP (/mcp, /health)
├── config.ts              zod-validated config; UGNAS_* env overrides win over the file
├── mcp/
│   ├── createServer.ts     McpServer wrapper
│   └── toolset.ts          all 39 tool registrations
├── safety/plan.ts         ConfirmationTokenService — the dry-run/confirm core
├── ssh/
│   ├── sshExecutor.ts      CommandExecutor interface + ssh2-backed SshExecutor
│   └── shellQuote.ts       shq() — every user value passes through it
└── services/              one class per tool group, each takes ServiceContext
    ├── systemService       status / info / pools
    ├── dockerService       containers / images / networks / compose
    ├── fileService         list / usage / find / thumbnail / mkdir / copy / move
    │                       / remove / upload / download / sync
    ├── backupService       create / list / verify / restore / schedule
    ├── networkService      interfaces / routes / ports
    └── util.ts             planOrExecute, path resolution, output parsers

One round-trip for many reads. Read-heavy tools batch commands behind ###NAME### markers and parse the sections from a single SSH call — system.info gathers OS, CPU, load, memory, uptime, thermals, disks, and the Docker version in one shot.

Chroot-aware SFTP. UGOS chroots SFTP to the share root: exec path /volume1/docker/x becomes SFTP path /docker/x. The sftpRoot config owns the mapping; thumbnails travel via base64-over-exec because /tmp sits outside the chroot.

BusyBox-tolerant. GNU-only flags (ls --time-style, find -printf) are probed once and cached; on BusyBox the file tools fall back to ls -1p and find -exec stat and keep working.

Setup

05 / 06

Configuration & wiring

The server reads a JSON config from ~/.ugnas-mcp/config.json (override with UGNAS_MCP_CONFIG). Environment variables win over the file — useful for CI and secret injection: UGNAS_HOST, UGNAS_PORT, UGNAS_USER, UGNAS_KEY_PATH or UGNAS_AUTH_TYPE=password + UGNAS_PASSWORD, UGNAS_DEFAULT_SHARE, UGNAS_HOST_KEY_SHA256. 

# ~/.ugnas-mcp/config.json
{
  "name": "home-nas",
  "host": "192.168.168.110",
  "port": 22,
  "username": "admin",
  "auth": { "type": "key", "privateKeyPath": "~/.ssh/id_ed25519" },
  "defaultShare": "/volume1",
  "commandTimeoutMs": 60000
}

Client wiring (stdio)

# official package — no clone, no build
npx ugnas-mcp                # or: npm i -g ugnas-mcp && ugnas-mcp

# client config
{
  "mcpServers": {
    "ugnas": {
      "command": "npx",
      "args": ["-y", "ugnas-mcp"],
      "env": { "UGNAS_MCP_CONFIG": "/absolute/path/to/config.json" }
    }
  }
}

Optional HTTP transport

stdio by default. Set UGNAS_HTTP_PORT to also expose a stateless streamable HTTP transport at /mcp (1 MiB body cap) plus /health. Loopback only, unless UGNAS_HTTP_ALLOW_REMOTE=1 — the endpoint carries no authentication, so put a proxy with auth in front if you need it off-box. 

UGNAS_HTTP_HOST=127.0.0.1 UGNAS_HTTP_PORT=4110 ugnas-mcp

POST 127.0.0.1:4110/mcp      # JSON-RPC, stateless
GET  127.0.0.1:4110/health   # liveness + target host

On the NAS

Required. SSH enabled (UGOS: Control Panel → Terminal & SNMP); the SSH user in the docker group; crontab access for scheduled backups; standard tools (tar, df, du, ip, ss — all present on UGOS).

Optional. rsync (only files.sync; the cp -a fallback covers its absence) and ffmpeg (only files.thumbnail).

Development

06 / 06

Build, test, verify

Users run npx ugnas-mcp from npm — everything below is for working on the server. CI (GitHub Actions) runs the same chain on every push and pull request. 

pnpm install
pnpm typecheck    # tsc --noEmit
pnpm test         # vitest — 38 tests, FakeExecutor, no NAS needed
pnpm build
pnpm smoke        # boots the built server, tools/list over stdio
pnpm smoke:http   # boots with UGNAS_HTTP_PORT, checks /health + /mcp
pnpm integration  # live-NAS checks (needs a reachable target)
pnpm publish      # prepublishOnly guard: typecheck → tests → build → smoke

Tests cover the confirmation gate, config validation, shell quoting, rsync gating, the output parsers, and a service↔tool wiring contract — the registered tool set is asserted to match the ledger above exactly, so a dead method or a missing registration fails the build. The suite runs against a FakeExecutor; no NAS is required.
